# Administering Messaging

Treat Messaging as an integration with user-owned provider environments, not a credential-sharing shortcut.

## Establish ownership

Record which user owns each provider account, application, workspace and conversation. Install and operate the integration in that environment.

Desktop delivery needs the relevant graphical session; a service or SSH login is not automatically the same credential context as the provider-owning user.

An AxiOwl account or license does not replace provider entitlement. Use the application's activation/account controls for their stated purpose.

## Account and formatting controls

AxiOwl account/activation controls have a separate purpose from provider sign-in. An offline entitlement or website login does not grant a model subscription or SSH access.

Where saved message-formatting controls are used, preserve the authored text and review the literal formatting selected. Formatting, sender provenance and license notices do not authorize another messaging operation.

## Plan the rollout

- Select the product, OS, architecture and channel.
- Keep provider applications installed through their own distributions.
- Choose the desktop and CLI integrations separately.
- Record selected components and actual installation outcomes.
- Review incomplete-integration warnings before assigning work through that surface.

Normal integration problems complete with warnings while independent selected work continues. Essential media, identity, elevation and package-engine safeguards still apply.

## Separate connection approvals

Choose remote routes deliberately. A phone approval, a relay peer, an SSH connection and an A2A endpoint are different grants.

For direct/server routes, document the listening address, network exposure and authentication. For SSH, preserve verified host keys and the intended remote user. A friendly node name is not an operating-system permission.

Do not expose a provider account more broadly merely to make a connection check pass.

## Maintain components

Use [Components and updates](components-and-updates.md). Save work before a provider update, allow the required application shutdown and read the actual installed result.

Published media and source changes do not update a running installation by themselves. Keep application, shared-runtime and provider-package versions distinct in your records.

## Backups and removal

Back up project material and required application state through your approved process. Message/operation records and diagnostics can contain sensitive text.

Use the product's ownership-aware uninstall and component controls. Removing Messaging is not a blanket request to delete provider accounts, all chat histories or unrelated credentials.

## Observe outcomes without duplicates

For an uncertain Send, preserve its operation reference and target identity. Inspect that operation or the native target when authorized. Do not submit duplicate work or delete its evidence to clear a status.

A registry entry, successful installation, reachable service and actual message delivery each establish something different.

## Collect support evidence

Include the application and component versions, operating system, selected provider surface, route, action, visible result and relevant time. Use narrow redacted logs or screenshots.

Exclude credentials, pairing offers and unrelated conversation history. Do not use historical compatibility claims as proof for a new release.
